## Prioritized gap checklist

### P0 — release blockers

- [ ] **Packet 2 — stabilize the plugin SDK.** Promote `@openrepurpose/platform-sdk` from a private
  `0.0.0` workspace package to an explicitly versioned compatibility boundary. Add a validated
  manifest with plugin/API versions, capabilities, configuration schema, and declared network,
  filesystem, secret, and child-process permissions. Define discovery/loading policy and the honest
  in-process trust warning, with third-party installation disabled or guarded by an advanced-code
  warning by default. Extend the reusable test kit into contract suites and run every first-party
  source and destination through them; source adapters already implement the shared interface, but
  publishing implementations are not yet uniformly exposed through the public SDK boundary.
- [ ] **Packet 3 — finish secrets and backup/restore together.** Preserve and version the existing
  AES-256-GCM `EncryptedFileSecretStore` fallback, decide whether supported hosts will use an OS
  credential store, and implement a tested, non-lossy migration/reconnect path from the v0.x vault.
  Add `openrepurpose backup create` and `backup restore <file>` with a versioned manifest, validation
  before mutation, safe settings/workflow/database export, external-media references, and default
  exclusion of secrets, large media, models, and derivatives. Add explicit encrypted secret export
  only if its threat model is acceptable, plus automatic pre-upgrade database backup where
  practical. No backup or restore command/service exists today.
- [ ] **Packet 4 — complete the focused security release pass.** Re-audit OAuth state/PKCE, secret
  migration and redaction, Origin/CSRF/host handling, LAN/TLS guidance, API/MCP authority, webhook

  execution. Add a regression test for every issue found, run a dependency audit, review GitHub
  Actions and release permissions, and add `SECURITY.md`. The v0.9 controls are a substantial
  starting point, not a completed 1.0 security sign-off.
- [ ] **Packet 5 — ship a reproducible Windows x64 artifact.** Select and document a maintained Node
  runtime/packaging strategy, add build metadata and a real CLI executable entry point, and prove a
  clean-user-profile install/start/doctor/UI workflow. The workspace is currently private, package
  versions are `0.0.0` or `0.1.0`, and normal users still need Node, pnpm, and workspace assembly.
- [ ] **Packet 6 — ship reproducible Linux artifacts.** Produce and smoke-test Linux x64 and decide
  Linux arm64 from measured dependency/CI reliability. Cover headless service startup, permissions,
  persistent paths, reverse-proxy deployment, and clean install/upgrade. Keep the existing Docker
  image as a separate technical-user distribution; its configuration tests pass, but an engine-backed
  build/smoke run and published-image workflow are still missing.
- [ ] **Packet 7 — settle licensing and third-party notices.** Obtain the maintainer's explicit
  OSI-license choice and add `LICENSE`; do not infer AGPL/MIT/Apache. Audit the exact packaged

  `THIRD_PARTY_NOTICES` with license, source, checksum/provenance, and source-offer/link obligations,
  or use a trusted first-run FFmpeg setup flow instead of bundling an unaudited binary.
- [ ] **Packet 8 — prove the upgrade and rollback matrix.** Add a stored, representative latest-v0.9

  schedules, source cursors, account metadata, and immutable execution data. Add backup/restore and
  failed-upgrade rollback tests. Existing tests cover migration integrity and selected populated
  v0.1-v0.4/v0.8 states, but not a released v0.9-to-v1.0 artifact path.

## Decisions

- Treat Packets 2-8 as the release-critical path before documentation polish or release-candidate
  certification. Packet 9 may prepare non-code documentation earlier where useful, but it must not
  substitute for artifact and migration evidence.
- Preserve the current local-first modular monolith, SQLite repositories, persistent job runner,
  `SecretStore`, platform adapter contracts, and deployment-neutral configuration; 1.0 work should
  harden these boundaries rather than create parallel systems.
- Treat the current encrypted local vault as a documented fallback until Packet 3 makes an explicit
  OS-keyring decision. Never include its key or plaintext secrets in a default backup.
- A source-workspace test pass is necessary but insufficient for 1.0. Release gates that mention an
  installation or artifact must execute against the produced Windows/Linux/Docker output.
- Licensing requires an explicit maintainer decision and is intentionally not selected by this audit.
