## Decisions

- The maintainer selected GNU Affero General Public License version 3 only (AGPL-3.0-only) for
  OpenRepurpose; root `LICENSE` contains the unmodified license text and root package metadata uses
  the matching SPDX identifier.
- Keep FFmpeg/ffprobe external in portable and repository Docker outputs until an exact build, codec
  configuration, license inventory, and provenance can be audited. Docker operators may create
  derived images with a specific FFmpeg build and must carry its notices/source provenance themselves.
- Pin the Docker Node.js base to the official multi-platform index digest; retain upstream Node and
  Debian system license files/notices from the base image, and do not add mutable APT packages to it.
- Treat Packets 2-8 as the release-critical path before documentation polish or release-candidate
  certification. Packet 9 may prepare non-code documentation earlier where useful, but it must not
  substitute for artifact and migration evidence.
- Preserve the current local-first modular monolith, SQLite repositories, persistent job runner,
  `SecretStore`, platform adapter contracts, and deployment-neutral configuration; 1.0 work should
  harden these boundaries rather than create parallel systems.
- Never include the encrypted vault, its key, or plaintext secrets in a default portable backup.
- A source-workspace test pass is necessary but insufficient for 1.0. Release gates that mention an
  installation or artifact must execute against the produced Windows/Linux/Docker output.
- Licensing requires an explicit maintainer decision and is intentionally not selected by this audit.
- Treat manifest permissions as reviewable declarations, not enforcement or isolation. Bundled
  plugins are statically composed; any future third-party loader must parse and policy-check inert
  manifest data before importing code.
- Keep the persistent destination job discriminator in the public SDK contract because it is stored
  data. Changing a first-party job type now requires a compatible migration.
- Use the versioned encrypted file vault as the common v1 implementation on Windows, Linux desktop,
  Docker, and headless Linux. Keep OS-native stores as future `SecretStore` adapters rather than
  making desktop keyring availability a runtime requirement.
- Keep portable backups secret-free. A secret-inclusive export would either co-locate the vault and
  key or require a separately reviewed memory-hard passphrase/KDF and recovery design.
- Use a single manifest-plus-SQLite container instead of a general archive: restore never extracts a
  manifest path, and size, SHA-256, SQLite integrity, and migration checksums are all verified first.
- Scope OAuth state lookup and one-time consumption by provider inside the repository transaction so
  a callback for one integration cannot consume another integration's pending state.
- Treat Basic authorization as the LAN browser gateway and bearer authorization as API-v1-only.
  Browser mutations retain session-bound Origin/CSRF enforcement; MCP remains a local stdio boundary
  with an allowlisted schema and no network listener.
- Treat all managed identifiers as cross-platform path segments even when running on Linux. Reject
  Windows reserved device names and trailing dots before filesystem resolution.
- Pin CI actions to full commit hashes and retain workflow-level `contents: read`; dependency review
  is a release check, not a runtime cloud dependency.
- Treat `0026_webhooks` as the final v0.9 schema boundary and record the non-destructive
  `0027_v1_compatibility` migration for v1. This deliberately creates the normal pre-upgrade backup
  while leaving the already-finalized v0.9 user schema and records unchanged.
- Pin the latest-v0.9 fixture to commit `fa974d48b86881159506094b33058c55433aee3c`, the
  final v0.9 commit before v1.0 work. Do not invent a release tag or artifact provenance that the
  repository never had; retain the fixture bytes as compatibility evidence when later migrations are
  added.

## Known issues

- Remaining release blockers and partial gates are enumerated in the prioritized checklist and
  release-gate snapshot above.
- Docker Desktop's Linux engine was unavailable during v0.9 Packet 6, so the existing Dockerfile has
  configuration/unit evidence but no recorded successful image build in this repository handoff.
- The Docker Desktop WSL distribution available on this Windows host has insufficient writable space
  for a release artifact build and remounted read-only after the attempted Packet 6 smoke. Do not use
  that attempt as Linux release evidence; wait for the new Ubuntu CI artifact job.
- No official v0.9 release tag or published database artifact exists. Packet 8 therefore pins its
  immutable latest-v0.9 fixture to the final v0.9 repository commit and records that limitation in the
  fixture manifest; it does not claim to have tested a nonexistent published artifact.
- Third-party plugin discovery/installation remains intentionally unavailable. The advanced load
  decision API requires an explicit in-process risk acknowledgement but does not sandbox code or
  enforce declared permissions; implementing a loader is outside Packet 2.
- Portable backups are intentionally uncompressed and secret-free. They require account reconnect
  and API-token recreation after restore; exact pre-upgrade/pre-restore database copies are local
  sensitive rollback artifacts, not portable exports.
- No OS-keyring adapter or secret-inclusive passphrase export ships in Packet 3. The documented
  encrypted vault remains the deployment-neutral v1 strategy and retains its same-user malware
  limitation.
- Third-party plugins still run in process and declared permissions are review metadata, not an
  isolation boundary. They remain disabled by default; sandboxing or a loader is outside Packet 4.
- LAN/headless operation still requires operator-managed TLS or a trusted reverse proxy. Packet 4
  tightened authentication but does not turn the local server into a managed internet-facing service.
- Security verification is source-workspace evidence. Packets 5-6 and 10 must repeat relevant checks
  against the actual Windows/Linux release artifacts.
- The repository Docker image omits FFmpeg/ffprobe; Docker media transforms require an
  operator-maintained derived image with its own documented FFmpeg provenance and notices. No
  engine-backed Docker build/smoke has been recorded on this host.
