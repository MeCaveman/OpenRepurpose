## Decisions

- Core/application code depends on the `JobRepository` and `JobHandler` boundaries; SQLite and the in-process runner are replaceable adapters and do not depend on browser or request lifetime.
- Claims use SQLite `BEGIN IMMEDIATE` transactions. Completion, failure, heartbeat, and cancellation transitions require the active lease owner, preventing a stale worker from overwriting recovered work.
- A handler must throw `JobExecutionError` to opt into retry and provide a deliberately safe public code/message. Unexpected errors are non-retryable and persist only `UNEXPECTED_JOB_ERROR` / `Job execution failed.` so raw exceptions cannot leak secrets.
- The runner claims only registered handler types. Packet 5 starts the runtime with no production handlers; later destination packets register their own implementations without a central provider switch.
- Idempotency keys are globally unique foundations for later workflow/source/destination keys. Job inputs are JSON-cloned before enqueue and never updated after creation.
- Destination integrations receive credentials only through `AdapterContext.secretStore`; publish requests/results and capability DTOs deliberately contain no secret values and can be safely projected to browser APIs.
- Destination registration is composition-based and rejects duplicate IDs, so later integrations do not require provider switch statements in core/application code.
- `PlatformError` separates stable category/code/retry metadata and a safe public message from its internal cause. Later destination jobs can map this classification into the existing job failure boundary.
- `SecretStore` defines get/set/delete by scoped reference only. The in-memory implementation remains test-only; Packet 7 supplies the protected local file implementation and documents its threat model.
- Adapter logging uses a sink-independent structured logger that recursively redacts sensitive keys, authorization/query/label forms, registered literal secrets, errors, cycles, and binary values. Fastify additionally redacts common credential paths and never serializes raw error messages or stacks.
- YouTube OAuth uses the current Google desktop-app loopback flow for v0.1, requests only `youtube.readonly` and `youtube.upload`, stores no access token, and derives capabilities from the scopes actually granted. OAuth state is persisted as a hash and bound to the initiating encrypted `SameSite=Lax` session; API mutations remain protected by Origin plus CSRF checks.
- The production `SecretStore` uses an AES-256-GCM file vault with a separate random 32-byte key and restrictive host file permissions. Its documented interim threat model protects against casual/vault-only disclosure, not a process or administrator that can read both files as the application OS user.

## Known issues

- No unresolved Packet 7 blocker. Live Google authorization was not run because it is optional/manual and requires user-owned credentials; automated coverage mocks every OAuth/YouTube HTTP call.
- The encrypted file vault is the documented interim local persistence mechanism; OS-native credential stores remain a later stable-release hardening target.
- A manual import against locally installed real FFmpeg/ffprobe remains to be performed on each supported OS, and the GitHub-hosted Windows/Linux matrix has not run until these changes are pushed.
- Live YouTube upload remains opt-in/manual with user-owned credentials; the resumable transport and all processing states are covered with mocked HTTP.
- Watched folders use portable periodic scans rather than platform-specific native-recursive watcher semantics; this deliberately favors reliable Windows, Linux desktop, and headless operation. A source file must be visible unchanged for the configured settling period before import.
- Live OAuth/upload and real FFmpeg checks remain opt-in/manual and require user-owned credentials and host-installed tools; release journeys use mocks by design.
