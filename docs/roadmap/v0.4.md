# v0.4 — Remote Sources + Automatic Ingestion

## Release goal

Turn OpenRepurpose from a cross-poster into a real Repurpose.io-style automation engine.

Primary new flow:

```text
Remote source account
       |
   new item detected
       |
       v
 persist + dedupe source item
       |
       v
 authorized media resolution
       |
       v
 download/copy into managed temporary storage
       |
       v
   workflow snapshot
       |
       v
 normal job/media pipeline
       |
       +--> destination A
       +--> destination B
       +--> destination C
       |
       v
 verify destination results
       |
       v
 retry unfinished destinations if needed
       |
       v
 cleanup temporary media
```

A remote source video does **not** need to already exist on the OpenRepurpose host.

If a configured source account publishes a new item, OpenRepurpose may detect it, resolve/download the authorized media into managed temporary storage, run the configured workflow, publish it to the selected destinations, and remove the temporary media after successful completion according to the configured retention policy.

Also formalize source polling, cursors, deduplication, source-item history, remote-media lifecycle, cleanup and restart recovery.

## Codex recommendation

- Default: **GPT-5.6 Terra, Medium**.
- Use **Sol High** only for dedupe/idempotency, crash recovery, cleanup semantics and content-rights boundary design.
- Luna for docs/tests/mechanical UI cleanup.
- Relative usage: **medium-high**.

## Rights and platform rule

Do not implement "download any public YouTube video."

A source item can be repurposed only when the user confirms they own it or are authorized to reuse it.

Prefer, in order:
1. original local media already linked to the source item;
2. officially provided download/export mechanism;
3. an explicitly enabled external downloader integration for authorized content only, with a rights confirmation and documented platform-terms caveat.

Never bypass DRM, members-only/private access, authentication, paywalls or other access restrictions.

Do not extract credentials/cookies from browsers.

A resolver/downloader is an implementation detail behind `MediaResolver`; source polling and workflow execution must not depend directly on a specific downloader implementation.

## Source architecture

Formalize `SourceAdapter` around:
- account/source identity;
- polling/event capability;
- cursor/watermark;
- item stable external ID;
- event ID where available;
- published time;
- observed time;
- metadata;
- resolution strategy;
- rights requirement;
- optional media availability.

Persist:
- source connection/config;
- cursor/watermark;
- last poll time;
- last successful poll time;
- last poll error;
- observed source item;
- source platform;
- stable external item ID;
- dedupe key;
- resolution status;
- linked local media ID when applicable;
- workflow execution ID(s);
- destination result state;
- cleanup/retention state.

Polling the same item many times must create at most one execution for the same enabled workflow/version policy.

A source item and its metadata must remain persistently recorded even after temporary media is deleted.

### Source item state

Use explicit source-item/media lifecycle state rather than inferring state from file existence.

A reasonable model is:

```text
OBSERVED
   |
   v
QUEUED
   |
   v
RESOLVING
   |
   v
MEDIA_READY
   |
   v
PROCESSING
   |
   v
PUBLISHING
   |
   +----> PARTIAL_FAILURE ----> RETRYING ----+
   |                                        |
   +----------------------------------------+
   |
   v
PUBLISHED
   |
   v
CLEANUP_PENDING
   |
   v
COMPLETED
```

Exact enum names may differ if the existing job model already provides equivalent states. Reuse existing job primitives instead of creating a duplicate job engine.

## Remote media lifecycle

Remote media is **ephemeral working data by default**. Metadata/history is persistent.

For each newly detected source item:

1. Persist the source item and stable dedupe identity before expensive processing.
2. Determine which enabled workflows subscribe to the source.
3. Apply source filters before downloading media whenever possible.
4. Resolve media through the configured `MediaResolver`.
5. If a matching managed/local original already exists, reuse it instead of downloading another copy.
6. Otherwise, if authorized resolution is available, download/copy the media into a job-scoped managed temporary directory.
7. Register the resolved media with the normal OpenRepurpose media/job pipeline.
8. Create a versioned workflow execution snapshot.
9. Publish independently to every configured destination.
10. Persist each destination result separately.
11. Retry only unfinished/failed destinations according to the existing retry policy.
12. Do not republish a destination already recorded as successful unless the user explicitly requests a republish.
13. Once every required destination has completed successfully, mark cleanup eligible.
14. Delete downloaded source media and generated temporary derivatives according to the retention policy.
15. Retain source metadata, workflow execution history, destination remote IDs/statuses and audit history after file cleanup.
16. If a process crashes/restarts at any point, recover from persisted state without uncontrolled duplicate publishing.

### Retention policy

Support at least:

```text
delete_after_success   # default for downloaded remote media
keep_for_duration      # e.g. keep for 24h before cleanup
keep_forever           # explicit opt-in
```

Exact configuration shape can follow existing project conventions.

Default behavior for remotely downloaded media:

```text
delete_after_success = true
```

Do not delete media merely because the first destination succeeds.

Cleanup eligibility requires all **required** destinations for that execution to have reached a terminal successful state.

If an optional destination is supported by the existing workflow model, its failure does not need to block cleanup once all required destinations succeed.

### Failure retention

When a workflow is incomplete or retryable:
- keep temporary media long enough for configured retries;
- do not redownload on every retry when the valid working copy still exists;
- allow cleanup of abandoned/terminally failed jobs after a configurable failure-retention window;
- never remove a user-owned original local file as part of temporary cleanup;
- cleanup may only delete files that OpenRepurpose owns/manages as temporary or generated artifacts.

### Managed temporary storage

Downloaded media must live under the existing managed data/storage root, never arbitrary current-working-directory paths.

Conceptually:

```text
data/
├── database/
├── jobs/
└── temp/
    └── <execution-or-job-id>/
        ├── source.<ext>
        └── generated/
```

Use the project's existing storage abstraction/path conventions if they differ.

Requirements:
- atomic/unique job-scoped paths;
- path traversal protection;
- predictable ownership;
- safe cleanup;
- recovery after restart;
- no deletion outside the managed temporary root.

## YouTube source

Use YouTube Data API for **detection/metadata**.

Prefer efficient channel-upload playlist polling over expensive broad search when appropriate.

Features:
- connect/select a channel the user controls or explicitly configures;
- discover new uploads after a stored cursor/watermark;
- optional filters:
  - include/exclude Shorts-like durations;
  - title regex/substring;
  - privacy/availability where accessible;
  - published-after;
- ingest title/description/published timestamp/video ID;
- dedupe after restart.

Media resolution:
- support "match local original" first;
- support official download/export mechanisms when the current platform API/account capability provides them;
- optional external downloader adapter can be enabled by the user for authorized content;
- downloader must be an external process with version detection and safe argument arrays;
- never pass secrets in command-line arguments when a safer mechanism exists;
- no credential extraction from browsers;
- no bypass of protected content;
- write output only into OpenRepurpose-managed temporary storage;
- register successfully resolved files with the normal media pipeline;
- clean downloaded media according to the retention lifecycle above.

Do not assume the YouTube Data API itself provides downloadable media bytes. Keep detection/metadata separate from media resolution.

### Optional generic sources

If usage permits, add:
- RSS/Atom media enclosure source;
- podcast feed source.

These are lower priority than YouTube and may be deferred within v0.4 if the release gate is otherwise met.

Generic sources must use the same `SourceAdapter` + `MediaResolver` + workflow/job pipeline instead of implementing their own publishing path.

## Workflow changes

Workflows now support:
- `local-folder:new-media`;
- `youtube:new-upload`;
- future source types through adapter registry.

Add source filters before job creation/download where enough source metadata is available.

Store source-item metadata in the workflow execution snapshot.

Template variables:
- `{{source.title}}`
- `{{source.description}}`
- `{{source.publishedAt}}`
- `{{source.externalId}}`
- existing file/media variables once media resolves.

A remote source must enter the **same normal workflow/job execution path** as local media after resolution. Do not create a second publisher/job system specifically for remote-source items.

Destination status must be independently persisted so a retry/restart can continue only unfinished destinations.

## Poll scheduler

This is not the full v0.5 scheduler.

Implement only a simple source poll loop:
- per-source next-poll time;
- configurable sane interval;
- persisted last success/error/cursor;
- jitter to avoid thundering herd;
- no polling faster than platform policy;
- pause source after repeated auth failure;
- graceful recovery after restart;
- do not require the localhost web UI to remain open;
- background polling must work in supported headless/self-hosted operation.

The poller only detects source items and feeds normal workflow execution. It must not directly publish media itself.

## Cleanup runner

Cleanup may be performed by the job runner or a small reusable cleanup service, but must remain separate from source-platform-specific code.

Requirements:
- only delete OpenRepurpose-managed temporary/generated files;
- cleanup is idempotent;
- missing already-deleted files are not fatal;
- persist cleanup state/error;
- retry cleanup safely after restart;
- never mark a workflow publication failed only because post-success cleanup temporarily failed;
- failed cleanup must remain visible and retryable;
- provide a stale-temp cleanup/reconciliation path for abandoned managed temp directories.

Do not build the full v0.5 scheduler for cleanup. Reuse the existing worker/background-runner primitives.

## Work packets

### Packet 1 — Source-domain design

Write ADR for:
- source item/cursor/dedupe semantics;
- observed vs completed state;
- source-item identity;
- workflow execution uniqueness;
- destination idempotency/retry behavior;
- remote-media ownership;
- retention/cleanup semantics;
- crash/restart recovery boundaries.

Implement schema/migrations and generic source contract tests.

The ADR must explicitly guarantee:
- source metadata survives temporary-file deletion;
- user-owned local originals are never deleted by remote-media cleanup;
- a restart cannot blindly republish destinations already recorded as successful.

### Packet 2 — Source polling runner

Implement persisted poll scheduling/recovery independent of destination job runner while reusing common primitives where sensible.

Requirements:
- runs without the browser/UI being open;
- persisted cursor and poll state;
- safe restart recovery;
- event/poll results persist source items before workflow creation;
- repeated polling of the same item remains deduped.

### Packet 3 — YouTube detection

Implement YouTube channel/upload detection with mocked API tests and quota-conscious API calls.

Keep detection/metadata independent from media download/resolution.

Test:
- new upload;
- same upload observed repeatedly;
- multiple new uploads;
- reordered API results;
- restart with existing cursor;
- filtered item never triggers unnecessary media resolution when filter can be decided from metadata.

### Packet 4 — Media resolution + temporary storage

Implement:
- local-original matcher;
- generic `MediaResolver` contract;
- managed job-scoped temporary media storage;
- resolution state persistence;
- media registration into the existing job/media pipeline;
- configurable retention policy model;
- idempotent cleanup primitives.

Optionally implement an external downloader bridge behind explicit configuration and rights confirmation.

External downloader requirements:
- fully separable/replaceable adapter;
- version detection;
- safe argument arrays;
- timeout/cancellation support;
- bounded output path under managed temp storage;
- no shell-string interpolation;
- no browser credential extraction;
- clear error mapping;
- partial-download cleanup or recovery;
- never bypass protected content.

Tests must cover:
- successful resolve;
- resolver failure;
- cancelled resolve;
- partial file;
- restart after download but before workflow execution;
- local original reused without copying/deleting the user's original;
- cleanup cannot escape managed temp root.

### Packet 5 — Workflow integration + destination recovery

Add:
- source filters;
- execution snapshots;
- template variables;
- exact-once-ish source dedupe semantics;
- independent persisted destination result state;
- retry of only unfinished destinations;
- cleanup eligibility after required destinations succeed.

"Exactly once" across remote APIs is not guaranteed; document the actual idempotency behavior precisely.

Required restart scenarios:
- crash before job creation;
- crash after job creation;
- crash after one destination succeeds;
- crash after all destinations succeed but before cleanup;
- crash during cleanup.

On recovery, already-successful destinations must not be blindly republished.

### Packet 7 — Restart, dedupe, retry and cleanup tests

Test at minimum:
- same page of source results returned repeatedly;
- process dies after item persistence but before job creation;
- process dies after job creation but before cursor advance;
- process dies after media download but before publish starts;
- process dies after destination A succeeds but before destination B starts;
- process dies after all uploads succeed but before cleanup;
- process dies during cleanup;
- workflow disabled mid-poll;
- two workflows subscribe to same source;
- source item cannot resolve media;
- resolver returns partial/corrupt output;
- failed destination retries without republishing successful destinations;
- temporary media remains available across retry when policy permits;
- successful workflow deletes managed temporary media under default retention;
- persistent source/job/destination metadata remains after media deletion;
- `keep_for_duration` delays cleanup;
- `keep_forever` prevents automatic cleanup;
- cleanup never deletes an original local file;
- cleanup cannot escape managed temp root;
- stale managed temp reconciliation is safe and idempotent.

Use mocked adapters/APIs. Do not require live social-platform publishing in CI.

## Acceptance criteria

- A mocked new YouTube upload automatically creates exactly the intended workflow execution(s).
- A remote source video does not need to exist on the OpenRepurpose host before detection.
- A newly detected authorized remote item can automatically resolve/download into managed temporary storage and enter the normal workflow pipeline.
- Source filters are applied before download when they can be evaluated from metadata.
- Restart scenarios do not cause uncontrolled duplicate publishing.
- A partially successful workflow retries only unfinished destinations.
- Successful destination results remain persisted across restart.
- Default remote-media retention deletes downloaded/generated temporary media only after all required destinations succeed.
- Temporary media is not deleted while required destination retries remain pending.
- User-owned local originals are never deleted by temporary cleanup.
- Job/source/destination metadata remains after media deletion.
- Cleanup is idempotent and restart-safe.
- No cleanup path can delete outside OpenRepurpose-managed temporary storage.
- Source polling works while the web UI is closed.
- Source polling does not use broad search unnecessarily.
- Rights confirmation is explicit for non-official download resolution.
- External downloader, if present, is optional and disabled by default.
- Detection and media resolution remain separate abstractions.
- Remote sources reuse the normal workflow/job/media/destination pipeline rather than creating a parallel publishing engine.
- v0.3 DB migrates cleanly.
- Standard checks pass.

## Stop boundary

Do not implement user-defined calendar schedules or the full transform pipeline yet.

Do not expand v0.4 into general-purpose cloud storage, permanent media hosting or arbitrary public-video downloading.

The v0.4 scope is:
- remote source detection;
- authorized media resolution;
- managed temporary ingestion;
- normal workflow execution;
- per-destination recovery;
- safe temporary-media cleanup;
- persistent metadata/history.
