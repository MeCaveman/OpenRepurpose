# v0.2 — TikTok Destination

## Release goal

Add TikTok as the second production-quality publishing destination without weakening the adapter architecture.

After this release:

```text
local media / watched folder
          |
          +--> YouTube
          |
          +--> TikTok
```

A workflow can publish independently to one or both destinations and retain per-destination status.

## Codex recommendation

- Default: **GPT-5.6 Terra, Medium**.
- Tests/docs: **GPT-5.6 Luna, Medium**.
- Escalate to **Sol High** only for a concrete OAuth/upload/audit constraint or idempotency issue.
- Relative usage: **medium**.

## Prerequisites

v0.1 release gate passes.

Read current official TikTok developer documentation before coding. As of the roadmap authoring date, Direct Post uses the Content Posting API and `video.publish`; unaudited clients have visibility/testing restrictions.

Verify rather than assume:
- current scopes;
- OAuth/PKCE requirements;
- direct-post eligibility;
- supported privacy values;
- creator-info preflight requirements;
- file upload limits/chunking;
- publish-status endpoint;
- request/rate limits;
- audit restrictions.

Official starting points:
- https://developers.tiktok.com/doc/content-posting-api-get-started/
- https://developers.tiktok.com/doc/content-posting-api-reference-direct-post/

## Non-goals

Do not:
- automate TikTok login with a browser;
- work around an API audit;
- scrape private creator endpoints;
- add unofficial device/emulator automation;
- add TikTok as a source yet;
- add full video transforms yet.

## Functional requirements

### Account connection
Add TikTok BYO app credentials/setup.

Connection flow must:
- use official OAuth;
- validate `state`;
- use PKCE when current TikTok docs require/recommend it;
- store tokens only through `SecretStore`;
- show granted scopes;
- show account identity;
- show whether direct/public posting is actually available.

### Capability model
TikTok adapter reports:
- supports video publish;
- allowed privacy options for this account;
- relevant duration/size/format constraints;
- whether a current app/account restriction forces private/testing visibility;
- caption/title limits;
- current publish availability.

Do not hardcode UI assumptions where creator-info/capability endpoints exist.

### Publish flow
Implement current official Direct Post sequence:
1. preflight creator/account information;
2. validate requested metadata/media;
3. initialize upload;
4. stream/chunk the local file as required;
5. complete upload;
6. poll status;
7. persist remote post/publish ID;
8. classify final state.

If publish is accepted but still processing, job status must distinguish:
- local upload complete;
- remote processing;
- remote success/failure.

### Multi-destination workflow semantics
One workflow execution can fan out:

```text
workflow execution
      |
      +--> destination job: YouTube
      +--> destination job: TikTok
```

A TikTok failure must not erase a successful YouTube result.

Add policies:
- `best_effort` default: other destinations continue;
- `all_or_nothing` is **not** supported because remote publishes cannot be safely rolled back.

### Platform metadata
Add destination-specific overrides while preserving common metadata.

Example:

```text
common.title
common.description

youtube:
  privacy
  category
  tags

tiktok:
  caption
  privacy
  disableComment
  disableDuet
  disableStitch
```

Only expose controls supported by current API/capabilities.

## Work packets

### Packet 1 — TikTok docs/capability ADR
Before production code:
- inspect current official docs;
- write `docs/adr/...-tiktok-direct-post.md`;
- record scopes, audit restrictions, upload flow and known limitations;
- update typed capability structures if needed.

Use **Terra**; use Sol only if the API semantics require a core architecture change.

### Packet 2 — OAuth/account adapter
Implement account connection, refresh, identity/capability query, mocked tests and setup UI/docs.

### Packet 3 — Publish transport
Implement init/upload/status with streaming and mocked HTTP fixtures. Test retry boundaries around chunked upload.

### Packet 4 — Destination fan-out
Refactor workflow execution only as much as necessary for multiple independent destination jobs. Add idempotency tests.

### Packet 5 — UI/CLI
UI:
- TikTok account card;
- platform limitations badge;
- per-destination metadata;
- job status.

CLI:
```text
openrepurpose accounts add tiktok
openrepurpose publish tiktok <media-id>
```

### Packet 6 — Release tests
Add mocked E2E for:
- TikTok private/test-mode restriction;
- rejected format;
- upload retry;
- remote processing failure;
- YouTube success + TikTok failure in same execution.

## Acceptance criteria

- No TikTok credentials/tokens appear in logs.
- Unsupported privacy values cannot be submitted.
- UI clearly surfaces audit/private-mode limitation rather than silently changing it.
- Large file path is streamed, not buffered into memory.
- Retry after a transient upload failure does not create an uncontrolled duplicate post.
- YouTube-only workflows from v0.1 remain compatible.
- DB migration from v0.1 fixture passes.
- All standard checks pass.

## Stop boundary

Do not begin Meta integration in this version.
