# v1.0 — Stable Open-Source Release

## Release goal

Ship a maintainable, installable Windows/Linux product with documented compatibility guarantees.

v1.0 is not primarily a feature release. It stabilizes:
- plugin SDK;
- database migrations;
- secrets;
- backups;
- packaging;
- release signing/checksums where feasible;
- docs;
- failure recovery;
- accessibility;
- security;
- upgrade path.

## Codex recommendation

- **GPT-5.6 Sol, High** for:
  - release architecture;
  - migration/security review;
  - cross-platform packaging failures;
  - plugin compatibility boundary.
- **GPT-5.6 Terra, Medium** for implementation.
- **GPT-5.6 Luna, Medium** for docs/changelog/test matrix cleanup.
- Relative usage: **very high**.
- Do not use Max unless a specific bounded blocker has resisted prior attempts.

## 1.0 product promise

A normal user can:
1. download an official Windows or Linux artifact;
2. run/install it;
3. start OpenRepurpose;
4. open the localhost dashboard;
5. run setup/doctor;
6. connect supported platforms using their own developer credentials;
7. create workflows;
8. stop/restart/upgrade without losing state.

A technical user can run:
- CLI;
- Docker;
- headless service;
- MCP/API.

## Licensing

Before public 1.0 release, the repository must contain an OSI-compatible license.

Default recommendation for this project:
- **AGPL-3.0** if the owner wants modified network-hosted versions to remain source-available to their users.
- Choose Apache-2.0/MIT instead if maximizing permissive reuse is more important.

Do not let Codex silently change the license. Record the chosen license in an ADR/maintainer decision.

## Stable plugin SDK

Promote adapter contracts to a versioned SDK.

Plugin types:
- destination;
- source;
- transcription provider;
- optional media transform extension only if it can be sandboxed/validated safely.

### Manifest
Define a manifest including:
- plugin ID;
- name;
- version;
- required OpenRepurpose API range;
- capabilities;
- configuration schema;
- permissions.

### Permission model
A plugin should declare what it needs:
- network hosts/domains;
- filesystem scopes if any;
- secret names/access;
- child process permission if applicable.

For v1.0, do **not** claim strong sandboxing if plugins execute in-process with application privileges. Document the trust model honestly.

Default third-party plugin installation may be disabled behind an "advanced/untrusted code" warning until a stronger isolation design exists.

### Compatibility
Semantic version plugin API.
Add contract test kit.

First-party integrations migrate to the same public-ish SDK interfaces where practical.

## Secrets

Finish production-grade secret storage.

Preferred order:
1. OS credential/keyring storage;
2. encrypted local vault with explicit threat model/fallback.

Requirements:
- migration from interim v0.x secret representation;
- no silent loss;
- backup excludes secrets by default unless encrypted export is explicitly requested;
- clear reconnect flow if tokens cannot be migrated.

## Backup/restore

Implement:
```text
openrepurpose backup create
openrepurpose backup restore <file>
```

Backup includes:
- DB;
- workflow definitions;
- settings safe to export;
- optional metadata.

By default exclude:
- OAuth tokens;
- client secrets;
- large media;
- transcription model binaries;
- cached derivatives.

Allow manifest describing external media paths.

Restore validates version/schema before touching current data.
Create automatic pre-upgrade DB backup where practical.

## Portable packaging

Goal artifacts:
- Windows x64;
- Linux x64;
- Linux arm64 if CI/dependencies are reliable enough.

Distribution may be:
- installer + portable archive on Windows;
- tarball/AppImage-like or packaged runtime on Linux;
- Docker image separately.

The essential requirement is that normal users do not have to manually assemble npm workspace dependencies.

### Node/runtime strategy
Choose and document a maintained packaging strategy after testing:
- bundled Node runtime + production JS/native modules;
- maintained executable packager;
- another reproducible approach.

Do not choose a tool because it was popular years ago; verify maintenance/current Node compatibility.

### FFmpeg
FFmpeg licensing must be addressed explicitly.

Before bundling FFmpeg:
- verify the exact build's license/components;
- include required notices/source offer/link obligations;
- document codecs;
- record checksums/provenance.

If that cannot be done confidently for v1.0:
- ship a first-run FFmpeg setup helper that downloads from a documented trusted source or accepts user-supplied path;
- do not illegally/recklessly repackage a random binary.

### whisper.cpp/models
Same principle:
- executable license notices;
- model license/source/checksum;
- model download remains user-controlled.

## v1.0 release gate

Do not tag 1.0 unless:

1. Clean Windows installation starts and opens localhost UI.
2. Clean Linux installation starts and opens localhost UI.
3. `openrepurpose doctor` catches missing/broken dependencies.
4. Upgrade from v0.9 preserves workflows/jobs/account metadata.
5. Secret migration either succeeds or gives an explicit safe reconnect path.
6. Backup/restore round trip succeeds.
7. FFmpeg transform and local subtitles work on release artifacts.
8. All first-party platform adapters pass contract tests.
9. No known uncontrolled duplicate-publish bug.
10. No known secret leakage in logs/UI/API.
11. MCP/API auth and webhook SSRF tests pass.
12. Default server binds loopback.
13. LAN mode is explicit/authenticated.
14. Plugin trust model is documented.
15. Third-party licenses/notices are present.
16. Full CI/release smoke suite is green.
17. Setup/platform limitations are documented clearly.
18. No required OpenRepurpose cloud service exists.

Track them as GitHub discussions/issues after 1.0.
