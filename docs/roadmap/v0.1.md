# v0.1 — Foundation + Local/YouTube MVP

## Release goal

Deliver the first genuinely usable OpenRepurpose build:

```text
Local file OR watched folder
          |
          v
      media import
          |
          v
   persistent workflow/job
          |
          v
     YouTube upload
```

The user can run a localhost dashboard and CLI, import local video, connect YouTube with BYO OAuth credentials, upload manually, and create a simple watched-folder -> YouTube workflow.

This release establishes architectural boundaries that later releases must reuse.

## Codex recommendation

- Architecture/security review: **GPT-5.6 Sol, High**, one bounded turn.
- Implementation: **GPT-5.6 Terra, Medium**.
- Tests/docs/cleanup: **GPT-5.6 Luna, Medium**.
- Relative usage: **very high**.
- Do not implement this release in one Codex turn.

## Non-goals

Do not add:
- TikTok;
- Meta;
- Twitch/Kick;
- remote YouTube-as-source downloading;
- Whisper;
- visual node editor;
- complex media transforms;
- Redis/Kafka/Temporal;
- multi-user accounts;
- hosted backend;
- auto-update.

## Functional scope

### Web
Routes/pages:
- `/` dashboard;
- `/setup`;
- `/accounts`;
- `/media`;
- `/workflows`;
- `/jobs`;
- `/settings`.

The setup screen checks:
- application data/config paths;
- database writable;
- ffmpeg found;
- ffprobe found;
- server bound to loopback;
- YouTube credential setup status.

### CLI
Implement:

```text
openrepurpose start
openrepurpose doctor
openrepurpose accounts list
openrepurpose accounts add youtube
openrepurpose accounts remove <id>
openrepurpose media import <path>
openrepurpose media list
openrepurpose publish youtube <media-id>
openrepurpose workflows list
openrepurpose jobs list
openrepurpose jobs show <job-id>
```

Add `--json` to list/show commands where useful.

### Data
At minimum model:
- `settings`;
- `accounts`;
- `media_assets`;
- `workflows`;
- `workflow_versions` or immutable execution snapshot equivalent;
- `jobs`;
- `job_attempts`;
- `job_destinations` or equivalent publish-result records;
- `source_cursors`;
- migration metadata.

Use UUID/ULID-like application IDs, UTC timestamps, foreign keys, indexes for job status/schedule queries.

### Media import
- Accept a local file path.
- Do not copy by default unless required; store a normalized absolute path plus stable metadata.
- Compute a content fingerprint suitable for duplicate detection without forcing the whole file into memory.
- Run `ffprobe` and persist duration, codecs, width, height, frame rate, audio presence, size.
- Missing/moved file becomes an explicit media state, not a crash.
- Support optional "managed library copy" setting if easy, but it is not required.

### Watched folder source
- User selects a directory.
- New supported files become media assets.
- Debounce partially-written OBS/render outputs.
- Require stable file size/mtime over a configurable settling period before import.
- Avoid duplicate imports after restart.
- Work on Windows and Linux.

### Job engine
Implement a SQLite-backed persistent runner:
- bounded worker concurrency;
- lease/heartbeat or equivalent crash-recovery mechanism;
- retry classification;
- exponential backoff + jitter;
- graceful shutdown;
- restart recovery;
- cancellation;
- immutable job input/snapshot;
- idempotency key per workflow/source item/destination as appropriate.

No external queue service.

### YouTube destination
Use official YouTube Data API/OAuth behavior.

Required:
- BYO Google developer credentials;
- installed/local OAuth flow where current docs support it;
- PKCE/state where applicable;
- scope no broader than necessary;
- refresh-token handling;
- resumable upload;
- title;
- description;
- privacy;
- category;
- tags if supported;
- upload progress;
- post-upload processing-status polling;
- typed rate/quota/auth errors.

Important product behavior:
- Explain that unverified API projects can be restricted by Google's audit/visibility rules.
- Never misrepresent a private/unverified upload as publicly published.

Official docs to verify at implementation time:
- https://developers.google.com/youtube/v3/guides/authentication
- https://developers.google.com/youtube/v3/docs/videos/insert
- https://developers.google.com/youtube/v3/guides/uploading_a_video

### Basic workflows
Support one trigger shape:

```text
watched-folder:new-media
  -> publish:youtube
```

Also allow a manual one-off publish that uses the same job/publish path.

Workflow fields:
- name;
- enabled;
- source config;
- destination account;
- title template;
- description template;
- YouTube privacy/category;
- created/updated timestamps.

Template variables at minimum:
- `{{file.name}}`
- `{{file.stem}}`
- `{{media.duration}}`
- `{{workflow.name}}`

Unknown variables must fail validation before execution.

## Security requirements

Before release:
- loopback bind by default;
- state-changing requests protected against cross-origin/CSRF abuse;
- tokens/secrets redacted from logs;
- credential persistence behind `SecretStore`;
- no client secret exposed in web bundle;
- server validates all paths and DTOs;
- upload OAuth callback validates state;
- job errors cannot dump Authorization headers.

## Acceptance tests

The release is blocked unless all are true:

1. `pnpm typecheck`, `pnpm lint`, `pnpm test` pass.
2. Web dashboard starts on loopback.
3. `openrepurpose doctor` reports actionable dependency/setup results.
4. A local video can be imported from both Windows/Linux-style test scenarios.
5. `ffprobe` metadata is stored.
6. Mocked YouTube OAuth/account connection works end-to-end.
7. Mocked resumable upload can survive a retry without creating a duplicate publish record.
8. A watched folder ignores a still-growing file, then imports it after settling.
9. Restarting while a job is `running` safely recovers it.
10. A workflow snapshot remains unchanged if the user edits the workflow after job creation.
11. Secrets do not appear in captured logs.
12. State-changing web requests from an invalid Origin are rejected.
